# 诊断与分析质量

## 目录

- 诊断顺序
- 指标不一致
- 空结果
- 异常诊断
- 时间完整性与观察窗成熟度
- 分组去重与可加性
- 身份和采集问题
- 证据标准

## 诊断顺序

按以下顺序排查，避免高成本或误导性分析：

1. 定义层。
2. 数据可用性和采集层。
3. 比较条件层。
4. 汇总结果层。
5. 分层结果层。
6. 样本和明细层。

指标定义未解决前，不得直接跳到原始 SQL。

## 定义层

比较以下内容：

- 分析模型；
- 事件或虚拟事件；
- 聚合方法；
- 分子和分母；
- 队列或统计人群；
- 用户身份和去重方式；
- 时间范围、时区和归因窗口；
- 筛选条件和逻辑关系；
- 分组和分桶规则；
- 退款、币种和延迟数据处理。

很多看似数据错误的问题，实际是不同定义计算出的合理结果。

## 指标不一致排查

1. 获取两侧完整定义。
2. 转换为同一比较模板。
3. 运行新查询前列出全部差异。
4. 使用共同基准口径复算两侧结果。
5. 判断差异项能否完整解释结果差距。
6. 对剩余差集抽取用户或记录验证。

将根因归类为模型、事件、时间、筛选、分组、身份或数据源差异。

## 空结果排查

检查最短链路：

1. 项目和权限。
2. 时间范围和时区。
3. 事件是否存在及近期是否有数据。
4. 筛选值和属性类型。
5. 请求中的分组、筛选逻辑和分析主体。

找到充分原因后立即停止，不要继续执行与根因无关的查询。

如果请求在访问 TA 前被输入结构或元数据校验拒绝，这不是业务空结果。先按错误路径
修正请求；只有工具成功且数据区为空时，才进入本节的业务排查。

## 异常诊断

先判断异常是否真实存在。

1. 确认指标定义没有变化。
2. 使用事件量、关键属性空值率和身份覆盖率检查采集完整性。
3. 检查延迟数据和时区边界。
4. 与稳定历史基线比较。
5. 量化偏离程度和样本量。
6. 拆分比率的分子和分母。
7. 下钻绝对贡献最大的维度。

只有基线足够稳定时才使用统计阈值。必须说明计算方法，未计算时不得声称显著。

## 时间完整性与观察窗成熟度

- 查询当天数据前，先判断自然日是否完整；当天小时数不足时默认排除，并在口径中说明。
- 同比或环比使用相同数量的完整自然日，不得用未完成当天对比历史完整日。
- 比较新版本、新渠道或新注册队列时，统一用户龄和转化窗口，例如都使用安装后 D7；
  不得直接比较不同上线日期版本的月累计付费率。
- 观察窗尚未成熟的版本只能作为预警信号，不能与成熟版本做确定性高低判断。
- 漏斗的结束日期是否限制起始事件、全部步骤或允许窗口向后延伸，必须依据模型返回的
  日期明细确认；不明确时缩小到已完全成熟的起始队列复算。

## 分组去重与可加性

- 按事件属性分组的去重用户可能跨组出现。例如用户在分析期内升级版本后，会同时计入多个
  `#app_version` 分组；各组人数不得相加还原总体去重人数。
- 需要稳定归因时优先使用安装版本、首次渠道等用户属性；需要分析行为发生时状态时才使用
  事件版本、事件国家等事件属性，并明确其快照语义。
- 对同一用户可能跨组的结果，同时保留总体去重值；分组只用于比较和贡献分析，不作为总体复算。
- 日去重人数之和代表用户日，不等于整段去重用户数。只有分子和分母都使用用户日口径时，
  才能计算基于日汇总的比率。

## 根因链

有效诊断需要连接多个层级：

```text
配置或产品变更
  -> 用户曝光或路径变化
  -> 行为指标变化
  -> 分层贡献变化
  -> 核心业务指标变化
```

每个箭头都需要证据。存在推断时标记为假设，并给出对应验证查询。

## 身份和采集问题

处理用户碎片化或跨端不一致时：

- 检查 `#distinct_id`、`#account_id` 和 `#user_id` 覆盖率；
- 按客户端和服务端上报来源拆分；
- 区分正常多角色行为与身份绑定缺失；
- 抽样同一设备或账号的登录、付费事件；
- 验证事件时间和绑定顺序。

验证埋点数据时：

- 对比实际事件清单和埋点方案；
- 验证属性类型和必填字段；
- 检查命名和大小写一致性；
- 统计关键属性空值率；
- 与稳定历史版本比较。

付费链路缺少支付失败、取消、商店回调或服务端票据事件时，只能将根因定位到责任版本、
商品和行为断点，不能仅凭客户端 `purchase_finish` 判断是真实扣款失败还是成功回调漏报。
金额字段全零或大面积为空时，不得用其交叉验证收入；应明确需要商店或服务端支付证据。

### 初始事件跨日重复

按天查询初始事件时，同一用户可能在多个日期重复触发安装、注册或激活事件。因此：

- 整段时间的去重用户数可能小于每日队列人数之和；
- 留存模型的每日队列汇总分母代表“队列成员次数”，不一定代表严格去重用户数；
- 必须同时查询整段去重人数与每日人数之和，并报告差值和比例；
- 不得把按日队列产生的活跃用户日分子直接除以整段去重人数；
- 需要严格新增用户 LT 时，应使用每个用户首次有效初始事件建立唯一队列，再按同一身份计算活跃用户日。

差异很小时也要披露，但不能未经用户级去重就声称已得到严格唯一用户口径。

### 模型与原始 SQL 的时间语义

事件分析或留存模型与原始 SQL 不一致时，优先检查：

- 项目时区；
- `#event_time`、`#server_time`、`$part_date` 的含义和转换；
- 客户端 `#zone_offset`；
- 模型使用的用户身份及账号合并规则；
- 时间边界是否包含当天未完成数据。

在 SQL 完整复现模型的时间转换和身份口径前，SQL 结果只能作为“不一致证据”，不得覆盖
模型结果。禁止仅凭表名正确或事件名相同就认定两种结果可比。

## 漏斗争议

用户触发全部事件却未被漏斗计入时：

1. 使用准确用户身份筛选。
2. 获取完整事件时间线。
3. 验证步骤顺序。
4. 验证完成窗口。
5. 验证首次事件和重复事件规则。
6. 验证每一步筛选条件。

只有满足模型规则后，才能继续判断是否存在数据丢失。

## 证据标准

优先级从高到低：

1. 准确定义或配置。
2. 直接查询结果。
3. 分层贡献。
4. 样本或用户时间线。
5. 行业基准或专家先验。

行业基准只能帮助建立假设，不能覆盖项目真实数据。

## 停止条件

出现以下情况时停止并说明证据不足：

- 必要元数据不可用；
- 关键事件没有采集；
- 样本量不足以支持目标推断；
- 计算 ROI 所需成本字段不存在；
- 对比周期使用不兼容口径；
- 查询接口返回权限错误。

明确缺少什么证据，以及获得证据所需的最小下一步。
