## 付费分析

### 付费率变化

1. 定义付费率及其分母。
2. 使用付费事件量和关键属性空值率验证上报完整性。
3. 拆分付费用户数和活跃用户数。
4. 按付费层级、渠道、版本和进度分层。
5. 定位付费前行为路径的变化。

检查分母增长和付费路径可达性之前，不得把付费率下降归因于付费意愿降低。

### 版本与渠道归因

付费率异常同时存在“版本问题”和“流量质量”假设时，按以下顺序验证：

1. 使用完整自然日确认总体付费率，并拆分活跃用户、付费用户和支付次数。
2. 按稳定渠道属性计算渠道规模与渠道内付费率，不只比较渠道占比。
3. 做渠道结构反事实：用历史渠道内付费率乘以当前渠道人数，计算当前渠道结构下的预期
   付费率。若预期未下降而实际下降，不得归因于渠道结构。
4. 使用统一成熟度的安装队列比较版本，例如安装后 D7 付费率；避免直接比较新旧版本月累计。
5. 在主要渠道内重复版本对比。版本在多个主要渠道内同向下降，才能排除单一渠道质量解释。
6. 下钻商品和购买步骤，优先查找能够解释绝对付费缺口最大的 SKU 或步骤。

版本分析需区分：

- `#app_version` 等事件版本代表行为发生时版本，用户可能跨版本重复计入；
- `install_version` 等用户属性适合稳定安装队列，但不代表用户当前版本；
- 上线过晚、观察窗未成熟的版本只能报告短期信号和样本量。

量化单个商品或步骤的解释度：

```text
该步骤解释度 = 该步骤按历史转化率计算的预期完成数 - 实际完成数
              除以版本整体预期付费数 - 实际付费数
```

事件分析中的商品点击和完成不一定属于同一用户、同一订单或同一商品。需要证明某个 SKU
的支付断点时，使用相同商品筛选的顺序漏斗，并统一身份和完成窗口。

### 首购分析

分析四个层级：

- 曝光：用户是否看到了商品或优惠；
- 吸引：用户是否查看了详细内容；
- 信任：用户是否开始支付；
- 可达：支付是否最终完成。

同时检查首次付费耗时和首单价格分布。

### 付费漏斗

使用真实事件定义浏览、商品选择、订单确认、开始支付和支付成功。
窗口必须符合实际购买路径。先定位最大流失步骤，再讨论促销策略。

如果商品曝光事件没有商品 ID，而点击和完成事件有商品 ID，不得按商品分组后把空曝光组与
具体商品点击直接相除。应从具备相同商品键的最早步骤开始构建商品漏斗。

支付完成事件缺少金额、支付失败、取消或服务端回调时，报告应区分：

- 已证实：哪个版本、渠道、商品和步骤发生转化下降；
- 未证实：真实支付失败、商店配置错误、票据校验失败或完成事件漏报中的具体技术机制。

### 复购分析

先确认续费事件和对应金额属性，再比较：

- 复购间隔；
- 获客渠道；
- 用户龄；
- 定价档位；
- 内容或产品变化；
- 季节性因素。

## LTV 与 LT

明确 LTV 公式：

```text
注册队列在指定周期内的累计收入
除以初始队列人数
```

说明收入是否包含付费收入、广告收入、退款、税费和多币种换算。

跨多个注册日计算 LT 时，不得直接平均每日队列的留存率或 LT。先按相对用户龄对齐，
再对人数做池化：

```text
R_d = 所有注册队列在相对第 d 日的活跃人数之和 / 所有注册队列初始人数之和
LT_Dn = sum(R_0 ... R_n)
      = D0 到 Dn 的活跃用户日总数 / 初始队列人数总和
```

完整执行规则、D55 边界、成熟队列和重复注册处理见
[lt-cohort-calculation.md](lt-cohort-calculation.md)。

### LTV 下降

按以下关系拆解：

```text
LTV = 付费渗透率 * ARPPU * 有效生命周期贡献
ARPPU = 人均付费次数 * 单次付费金额
```

先定位变化因子，再下钻商品或行为。

### 回本进度

当 ThinkingData 中存在成本字段时，将各观察日累计 LTV 与 CAC 比较，报告：

- 当前观察日；
- 当前累计 LTV；
- CAC；
- 当前回收比例；
- 与回本线的差距。

## 游戏系统

### 关卡流失

1. 查找流失用户最后尝试或完成的关卡。
2. 按关卡计算流失集中度。
3. 比较通关率、尝试次数和失败后回访率。
4. 对比新用户和老用户。
5. 检查教学引导和机制切换完成率。
6. 区分数值难度、玩法设计和引导问题。

### PVP 平衡

- 按段位、战力、英雄、阵营和匹配条件比较胜率。
- 谨慎分析胜率分桶与留存、付费的关系。
- 控制玩家能力和成长进度差异。
- 样本量不足时合并分桶并明确说明。

### 新角色或新英雄

建立可比对照组，并检查：

- 获取路径和付费；
- 养成投入；
- 使用率和胜率；
- 分段位表现；
- 阵容多样性及对同定位角色的挤压；
- 获取后的留存和参与度。

不得仅根据全局胜率建议调整平衡性。

### 活动效果

分离自然增长和活动增量。使用活动前周期、对照组或经过校准的历史基线。
拆分新老用户，重建参与漏斗，并区分 GMV 上涨和真实增量价值。

## 用户分析

### 流失定义

根据真实回访概率确定未登录阈值，不能使用争论结果或通用默认值。
量化不同阈值的误判率，再使用渠道、设备、进度、社交和付费维度构建画像。

### 单用户排查

先从对应模型用户列表取得真实 `user_id`，再查询有限时间范围内的事件序列。用户属性
需要通过用户属性分析或只读 SQL 补充，当前工具没有独立的“用户画像”查询入口。
按业务链配对事件，例如 `order_create`、`pay_callback` 和 `item_grant`，最后判断问题
是单用户还是影响了更大人群。

### 标签分析

先查询现有分群或标签的列表和详情；只有确需判断刷新状态时再查询刷新进度。
结合用户属性分析查看标签人群组成。当前能力只读，不创建、更新或刷新分群和标签。

## 获客与运营

### 渠道质量

在同一口径下比较规模、留存、付费、LTV 和行为丰富度。成本字段存在时再计算
CAC、CPI 和 ROI。使用多个信号检测异常流量，禁止只按 CPI 或 CTR 分配预算。

### 广告投放

综合分析获客、激活、付费和留存。存在广告成本字段时再分析回收，重点比较绝对消耗和价值贡献。
预算调整建议必须附带验证周期和边际成本保护条件。

### 定价

先确定目标是最大化收入、渗透率还是利润。存在历史价格和购买数据时再比较价格变化后的转化差异。
将价格与真实付费金额分布和用户分层比较。竞品定价只能作为背景，不能直接证明最优价格。
