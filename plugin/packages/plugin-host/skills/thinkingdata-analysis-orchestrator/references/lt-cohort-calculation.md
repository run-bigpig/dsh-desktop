# 跨日队列 LT 计算

## 适用场景

用于一个自然周、月或自定义注册区间内的新用户 LT，尤其适用于：

- 注册跨多个日期；
- 不同注册日的观察窗长度不同；
- 需要 D7、D30、D55 或共同成熟窗口 LT；
- 日队列人数之和与整段去重人数不一致；
- 留存模型结果需要拆分后合并。

## 先固定定义

查询前明确：

- 初始事件，例如安装或注册；
- 活跃事件；
- 用户身份；
- 项目时区；
- 注册区间；
- 截断日是 `D0-Dn` 还是总共 `n` 个自然日；
- 当天未结束时是否排除当天；
- 结果是成熟窗口 LT、截至当前的删失累计 LT，还是最终 LT 预测。

不得把以下三个指标混称为“LT”：

1. `LT_Dn`：所有队列都完整成熟到 Dn 的累计留存面积；
2. 截至当前 LT：不同队列按各自已观察长度累计，存在右删失；
3. 最终 LT：需要尾部模型或足够长的完整历史，不能由短窗口直接宣称。

## ThinkingData 留存请求模板

留存模型使用：

- `event_view.stat_type`: `retention` 或 `lost`；
- 初始事件 `type`: `first`；
- 回访事件 `type`: `second`；
- `time_particle_size`: 日 LT 使用 `day`；
- `unit_number: n`: 返回到 Dn，而不是总共 n 个自然日。

示意：

```json
{
  "project_id": 123,
  "event_view": {
    "start_time": "2026-01-01 00:00:00",
    "end_time": "2026-01-07 23:59:59",
    "time_particle_size": "day",
    "stat_type": "retention",
    "unit_number": 55
  },
  "events": [
    {"event_name": "register", "type": "first"},
    {"event_name": "app_start", "type": "second"}
  ]
}
```

已验证的日留存返回结构中，`state_avg["0"]` 是计算 LT 所需的逐日回访序列：

- `stageValues[0]`：初始人数展示位；
- `stageValues[1]`：D0 活跃人数；
- `stageValues[2]`：D1 活跃人数；
- `stageValues[n + 1]`：Dn 活跃人数。

`state_avg["1"]` 是辅助的未回访或剩余状态序列，通常单调变化，禁止把它求和当作 LT。
解析前应使用单日小样本验证索引，防止服务端版本或模型配置改变返回结构。

### 推荐调用顺序

1. 用事件分析确认初始事件和活跃事件在目标周期有数据；
2. 用单个注册日、`unit_number: 1` 验证留存参数；
3. 用同一个注册日扩展到目标 `unit_number`，验证数组长度和索引；
4. 再扩展注册范围；
5. 整段失败时只拆注册范围，不改事件和观察窗；
6. 在工具调用内部提取 `initNum`、`stageValues` 和日期，避免完整矩阵撑满上下文。

`event_view.stat_type` 虽然在部分工具描述中只是普通字符串，服务端实际只接受
`retention|lost`。传入 `user` 等值会收到 `-1008` 正则校验错误。事件 `type` 使用
`first`、`second` 或指标展示用的 `simultaneous_display`，不要自行发明枚举。

## D55 边界

`unit_number: 55` 返回 D0 到 D55，共 56 个用户龄日。

- 标准 `LT_D55`：求和 D0-D55；
- “总共 55 个自然日”：求和 D0-D54。

输出必须明确使用哪一种，不得只写“55 天 LT”。

## 多队列正确加权

设第 c 个注册队列初始人数为 `N_c`，相对第 d 日活跃人数为 `A_c,d`：

```text
R_d = sum_c(A_c,d) / sum_c(N_c)
LT_Dn = sum_d=0..n(R_d)
      = sum_c sum_d=0..n(A_c,d) / sum_c(N_c)
```

执行时优先合并人数，不合并百分比：

1. 每个注册日只保留初始人数和 D0-Dn 活跃人数；
2. 对相同相对用户龄的活跃人数求和；
3. 初始人数求和；
4. 用合并后的活跃人数除以合并后的初始人数；
5. 对 D0-Dn 留存率求和得到 LT。

每日 LT 的算术平均只有在每日新增人数完全相同时才严格等价。即使本次差异很小，也不能
把简单平均当作通用方法。

## 观察窗和右删失

当注册跨多个日期时，最年轻队列决定共同成熟窗口：

```text
共同完整用户龄 = 最后一个完整数据日 - 最晚注册日
```

当天尚未结束时，使用前一天作为最后完整数据日。例如当前为 7 月 24 日，1 月 31 日队列
通常只能稳定报告到 7 月 23 日对应的完整用户龄。

比较渠道、月份或版本时，必须使用相同的共同成熟窗口。把老队列多出来的观察日计入、
同时让新队列停在较短窗口，会使结果混合了用户质量和观察长度。

如果业务确实需要“截至当前累计 LT”，可以按每个队列各自已观察长度累计活跃用户日后，
再除以全部初始人数，但必须标记为右删失结果，不能与成熟 `LT_Dn` 或最终 LT 直接比较。

## 查询拆分与合并

“长注册区间 × 长观察窗”的日留存请求可能返回通用 `-1004`、超时或过大结果。恢复顺序：

1. 保留事件、身份、时区、`unit_number` 和过滤条件；
2. 先用单个注册日验证请求和返回索引；
3. 将注册区间拆成不重叠的小块，例如 7 天一块；
4. 并行查询各块；
5. 只抽取初始人数和逐用户龄活跃人数；
6. 按上一节公式合并；
7. 校验分块初始人数之和等于按日队列人数之和。

不得因为整段请求失败就缩短观察窗、改变事件或更换身份；这些变化会悄悄改变问题定义。

分块彼此独立时可以并行调用，但必须满足：

- 日期块不重叠且无缺口；
- 请求除起止时间外完全一致；
- 每块成功后只保留紧凑结果；
- 任一块失败时单独恢复该块，禁止把已成功块全部重跑；
- 外层执行器返回“仍在运行”的 cell 或 session ID 时，使用 wait/poll 继续取结果，
  不得重新提交相同 TA 查询。

## 去重与重复初始事件

至少运行两个交叉检查：

1. 整个注册区间的初始事件去重用户数；
2. 每日初始队列人数之和。

若两者不同，说明同一用户可能跨日重复触发初始事件，或模型身份存在合并规则：

- 留存模型池化结果使用按日队列人数作为一致分母；
- 严格唯一新增口径需要按用户首次有效初始事件去重后重建队列；
- 不得把池化活跃用户日除以整段唯一用户数；
- 输出中报告两种人数、差值、比例及其对解释的限制。

## SQL 交叉验证

标准留存模型能表达问题时，以模型为主。SQL 只用于严格首次事件去重或模型复现。

SQL 前必须确认：

- 真实事件表；
- 模型时区和日期转换；
- `#event_time`、`#server_time`、`$part_date` 的关系；
- 模型用户身份；
- D0 的同日边界；
- 分区覆盖了时区转换可能跨越的相邻日期。

如果 SQL 的每日新增、整段去重人数或 D0 留存无法与模型对齐，立即停止使用 SQL 计算 LT。
保留差异作为数据质量证据，回到模型结果；不得在未解释冲突时挑选更符合预期的数字。

## 最小输出

至少报告：

- 项目、初始事件、活跃事件和身份；
- 注册区间及项目时区；
- 整段去重新增与按日队列人数之和；
- `LT_Dn` 的 Dn 定义；
- D1、D7、D30 和最后观察日留存；
- 活跃用户日总数、分母和最终 LT；
- 共同成熟窗口；
- 简单平均与人数池化差异是否足以解释业务争议；
- 数据重复、删失、SQL 不可比或当天未完成等限制。
