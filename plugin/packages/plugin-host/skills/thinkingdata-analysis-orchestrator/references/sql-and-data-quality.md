## 何时使用 SQL

标准事件、漏斗、留存、分布、间隔、路径和用户属性问题优先使用对应分析模型。
以下情况使用 SQL：

- 模型接口不支持的表关联；
- 原始记录验证；
- 元数据检查；
- 自定义窗口计算；
- 复现模型计算结果。

不能只因为熟悉 SQL 就绕过分析模型。

## SQL 工具选择

- 结果很小、预计 30 秒内完成：使用 `ta_query_sql`。
- 需要控制 `page_size` 的中等结果：使用 `ta_execute_sql`。
- 已知扫描大、计算复杂或可能超过同步超时：直接使用 `ta_submit_sql`，不要先让同步
  查询超时。
- 异步查询提交后，使用返回的 `task_id` 查询状态；完成后从 `page_id: 0` 开始逐页
  获取结果，直到返回结果表明没有下一页。
- `ta_execute_sql` 也可能只返回 `taskId`、表头和页数，而不直接返回数据行。此时无需
  查询任务状态，直接使用该任务 ID 从 `page_id: 0` 调用 `ta_sql_result_page`。
- 只有当前工作流提交的任务确定不再需要时才取消；不要取消来源不明的任务。

同步工具的 `timeout_seconds` 范围是 1 到 300 秒。`ta_execute_sql` 的 `page_size`
运行时校验下限为 1000，上限为 100000；即使工具描述显示更小值可用，也以服务端实际
错误为准修正为至少 1000。没有证据需要调大时使用 1000，避免一次返回过多内容。

## 字段确认流程

1. 复用已经确认的项目、事件、属性和身份字段。
2. 只有字段未知或 SQL 报列不存在时，才检索对应元数据。
3. 无法从元数据确定真实表结构时，可以尝试 `SHOW` 或 `DESCRIBE`；若返回权限错误，
   不得重复调用，改用元数据工具、已知模型结果或带日期分区的最小 `SELECT` 验证。
4. 确认字段类型、分区字段、日期覆盖范围和关联键。
5. 生成能够回答问题的最小查询。

禁止根据显示名猜测字段名。

若存在可靠的事件表命名约定，可以从已确认的 `project_id` 生成候选表名并做一次最小
只读验证。服务端若识别该表并提示必须添加 `$part_date`，说明候选表存在；添加最窄分区
后读取一行确认字段。此方法只能确认表和字段，不能确认 SQL 已复现分析模型的时区、身份
或去重逻辑。禁止枚举多个表名试探。

## 只读安全边界

这是不可覆盖的硬约束。任何 SQL 工具调用前都必须验证完整语句绝对只读；工具名称、接口权限
或服务端只读校验不能替代调用前检查。

只允许单条：

- `SELECT`；
- `WITH ... SELECT`；
- 内层语句也满足本节约束的 `EXPLAIN` 或 `EXPLAIN ANALYZE`；
- `SHOW`；
- `DESCRIBE`。

检查完整 SQL，包括全部 CTE、子查询、注释后的实际语句和 `EXPLAIN` 内层查询。`WITH`
不是天然只读，最终语句及每个 CTE 都必须只读。允许一个可选的末尾分号，但禁止出现第二条
非空语句。

禁止生成或执行任何可能产生副作用的 SQL，包括但不限于：

- DML：`INSERT`、`UPDATE`、`DELETE`、`MERGE`、`UPSERT`、`REPLACE`、`TRUNCATE`；
- DDL：`CREATE`、CTAS、`ALTER`、`DROP`、`RENAME`、临时表、临时视图；
- 数据搬运：`COPY`、`EXPORT`、`UNLOAD`、`LOAD`、`IMPORT`、`SELECT INTO`；
- 过程与动态执行：`CALL`、`EXECUTE`、存储过程、可能写入数据或外部系统的函数；
- 权限与安全：`GRANT`、`REVOKE` 及角色、用户、策略修改；
- 事务与会话：`BEGIN`、`START TRANSACTION`、`COMMIT`、`ROLLBACK`、`SET`、`RESET`、`USE`；
- 维护与元数据修改：`ANALYZE`、`VACUUM`、`OPTIMIZE`、`REFRESH`、`REPAIR`、`MSCK` 等。

即使用户明确授权或要求写操作，也不得执行或提供可直接执行的写 SQL。改为提供只读检查、
影响范围评估或说明该操作超出本 Skill 安全边界。无法确定某个语句、函数或连接器是否有
副作用时，按不安全处理并停止 SQL 调用。

## ThinkingData 与 Trino 约定

- 包含 `#`、`$` 或保留字的标识符使用双引号。
- 添加日期分区过滤。
- 对事件表执行最小样本查询时也必须带 `$part_date`；`SELECT ... LIMIT 1` 不能替代分区过滤。
- 事件表存在事件分区时添加对应过滤。
- 明确时间边界和时区假设。
- 不查询无用字段。
- 探索阶段默认添加保守的 `LIMIT`。
- 引擎不允许时，不在 `GROUP BY` 中使用查询列别名。
- 禁止无 `LIMIT` 的全表排序。

## 性能优化流程

1. 修改前完整阅读原 SQL。
2. 使用 `EXPLAIN` 检查静态执行计划。
3. 仅在实际执行安全且必要时使用 `EXPLAIN ANALYZE`。
4. 检查分区裁剪和扫描行数。
5. 查找重复子查询、宽字段读取、全局排序和行数膨胀关联。
6. 一次只修复一个根因。
7. 将优化结果与原查询逐项比较。

在 Trino 类分析系统中不得习惯性建议增加索引。

## 结果验证

重写或优化后的 SQL 必须保持：

- 列数量；
- 列名；
- 行的业务含义；
- 需要集合相等时的行数；
- 数值精度；
- 空值处理；
- 时区行为。

结果过大时，使用哈希、分组校验和及定向抽样比较。

## SQL 生成输出

输出以下内容：

1. 假设和已解析元数据；
2. SQL；
3. 参数和时间范围说明；
4. 预期结果列；
5. 安全与性能说明；
6. 必要时提供验证查询。

只有工具执行成功后，才能声称 SQL 已经运行。

## 失败恢复

- 只读校验失败：删除多语句或写操作；不要尝试混淆关键字绕过校验。
- 用户要求执行写 SQL：拒绝生成和执行写语句，改为只读诊断；用户授权不能覆盖安全边界。
- 无法判断函数或连接器是否写外部系统：停止执行，不以“可能只读”为由尝试调用。
- 列或表不存在：先用元数据、`SHOW` 或 `DESCRIBE` 确认真名，只改对应标识符。
- `SHOW` 或 `DESCRIBE` 权限不足：停止该发现路径，切换项目元数据或带分区的最小查询。
- 提示事件表缺少 `$part_date`：添加最窄可用日期分区，不要仅添加 `LIMIT` 重试。
- `ta_execute_sql` 返回 `pageSize` 下限错误：只把 `page_size` 修正为 1000 或更大。
- `ta_execute_sql` 成功但没有数据行：从返回的 `taskId` 调用 `ta_sql_result_page`，不要
  把元数据响应误判为空结果，也不要重新执行 SQL。
- 同步超时：若查询本身合理，保留 SQL 并改走异步链路，不要先扩大扫描范围重试。
- 响应过大：缩小列、时间和分组，或使用分页/异步结果页；不要改用下载工具规避分析。
- TA 执行错误：保留错误信息和原 SQL，一次只验证一个修正假设。

## 数据质量检查

根据问题选择检查项：

- 实际事件数与埋点方案对比；
- 属性类型一致性；
- 必填属性空值率；
- 重复事件或订单 ID；
- 客户端和服务端上报完整性；
- 时间戳延迟和时区边界；
- 用户身份覆盖率；
- 同一业务链事件之间的数量和身份一致性。

必须分开判断数据采集正确性和业务表现。
